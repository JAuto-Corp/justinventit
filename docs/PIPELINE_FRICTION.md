# Pipeline friction — scope (JV-owned, JA is the first adopter)

Status: **adopted** (o, 2026-09-30). The owner approved the direction; technical choices are delegated to the director.
Evidence: JA gate inventory, `customer-portal` branch `claude/gate-inventory`,
`docs/agentic/pipeline-friction/GATE-INVENTORY.md` (122 rows / 120 gates, base `b049a64b`).

## Intent

Every gate the pipeline runs should protect something a real reader would care about, and should cost roughly what it
catches. Today that isn't true. Most of the gates came from real incidents, and none has ever been retired. Four
generated-artifact gates alone produced 130 regeneration commits since 2026-09-01, about 11% of all staging commits.
Product PRs also pay for 27 gates that only check orchestration tooling. The goal: a red means something, and a
product slice pays only for checks on what it touches, **without weakening any protection that has caught a real defect.**

## Invariants

- **I1. No protection is lost silently.** A gate is moved, merged or retired only with a written reason, and only after
  confirming what it protects is still covered elsewhere (another gate, a generator, or an accepted residual).
- **I2. Generated artifacts are regenerated by machines, not PR authors.** A PR never fails only because a generated
  file needs a rerun. Staging (or the PR itself) regenerates it and commits it, following the existing `database.types.ts`
  auto-regen pattern. Drift in the *generator's inputs* still fails.
- **I3. Product PRs run only JV gates their paths can affect.** A JA PR that touches no orchestration path doesn't run
  orchestration-only gates. JV/tooling PRs still run them in full, and staging/main pushes run everything.
- **I4. Local pre-ci stays a superset of the hosted fast lane** (it's derived from the same sources: `pre-ci.sh` and the
  census). Any scoping in I3 applies to both, identically.
- **I5. Every gate has an owner and a measured false-red rate.** The rate comes from repo history (adjust/regen/excuse
  commits) plus the CI record. A gate whose false reds exceed its real catches for a review period goes to the director for
  keep / redesign / retire.
- **I6. Each gate runs once per suite.** No gate executes twice in one run.

## Non-goals

- The full JA → JV extraction of orchestration machinery (the separation program). This plan is the in-place step that
  makes that move smaller later.
- Weakening any money, security, migration or tenant-isolation gate. Those only get cheaper through I2/I6, never removed.
- Scenario-test infrastructure redesign (ephemeral CI databases, JA #3711), which stays on its own track.

## Sequencing and bandwidth (owner rule: must not distract JA invoicing)

- **One JA adoption PR open at a time**, authored by one seat on its cheaper setting (d). Reviews use the Opus pinned
  reviewer. It merges only in gaps between invoice landings, never ahead of one.
- Changes to the CI workflow file (W1–W3) land only with `pre-ci.sh` green, one trial PR, and a single-commit revert
  ready.
- Order: see Decisions below.
- JV owns this document and any generic design (the pre-ci derivation, the gate-ledger schema, the auto-regen pattern).
  JA gets thin adoption PRs that cite it, the same way REVIEW_PRACTICE v1 was adopted.

## Measurement

Tracked on the provider-pattern scoreboard (host) and in the JA gate ledger once W6 exists:
- paid CI rounds per landed slice, split into product-caused and process-caused;
- regeneration commits per week (W1 target: roughly 0 hand-regenerations);
- hosted minutes per product PR (the W2/W3 effect);
- standing authorities in use (the target is to retire 3 and 5).

Baseline (2026-09-29): the #3755 repair took 4 hosted CI rounds, 2 of them process-caused. 130 artifact regen commits
since 09-01.

## Decisions (director, 2026-09-30; the owner delegated technical choices)

1. **W1 regenerates on staging after merge**, following the existing `database.types.ts` pattern. PR diffs stay clean, and the PR
   gate checks only that the generator's inputs are valid.
2. **Order: W3 → W4 → W1 → W2 → W5 → W6**, with W7 whenever a seat is idle. W4 is small and removes a production secret
   from CI, so it goes right after the zero-risk de-duplication, ahead of the larger W1/W2 workflow changes.
